# Backup Encryption

`docker-sqlite-backup` can encrypt every backup archive with AES-256-CBC before it is compressed and uploaded to storage. Encryption is off by default and is controlled by configuration and a single 256-bit key.

## Overview

| Item | Value |
|------|-------|
| Cipher | AES-256 (`Aes.Create()`, 256-bit key) |
| Mode | CBC (.NET default) |
| Padding | PKCS7 (.NET default) |
| IV | 16 bytes, random per file, generated by `GenerateIV()` |
| Authentication | None (no HMAC or AEAD tag) |
| Output suffix | `.enc` |

The encrypted file layout is:

```
[16-byte IV][AES-256-CBC ciphertext]
```

The IV is prepended to the ciphertext so decryption needs only the key.

## Pipeline position

Encryption runs inside `BackupService.ExecuteBackupAsync`:

1. The SQLite database is copied to a plaintext backup file.
2. The plaintext file is encrypted to `<backup>.enc` and the plaintext file is deleted.
3. If compression is enabled, the `.enc` file is compressed.
4. The result is uploaded to the configured storage backend (local, S3, or Azure).

Because encryption happens before upload, the storage provider never sees plaintext backups.

The `BackupManifest.IsEncrypted` flag is set when the backup file name ends with `.enc`.

## Configuration

| Setting | Environment variable | Purpose |
|---------|----------------------|---------|
| `AppSettings.EnableEncryption` | `BACKUP_AppSettings__EnableEncryption` | Turns encryption on (default `false`). |
| `AppSettings.EncryptionKey` | `AppSettings__EncryptionKey` | Base64-encoded 32-byte key. |
| (key override) | `BACKUP_ENCRYPTION_KEY` | Base64-encoded 32-byte key. Takes precedence over `EncryptionKey`. |

Example `docker-compose.yml` fragment:

```yaml
services:
  sqlite-backup:
    environment:
      BACKUP_AppSettings__EnableEncryption: "true"
      BACKUP_ENCRYPTION_KEY: "${BACKUP_ENCRYPTION_KEY}"
```

Store the key in an environment file or secret manager, not in `appsettings.json`.

### Key resolution order

1. `BACKUP_ENCRYPTION_KEY` environment variable, if set and non-empty.
2. `AppSettings.EncryptionKey` (bound from `AppSettings__EncryptionKey` or `appsettings.json`).

If `BACKUP_ENCRYPTION_KEY` is set but empty, the empty value is used as the key and the lookup stops there. Make sure the variable is either set to a valid key or unset.

## Key format

- Base64-encoded
- Exactly 32 bytes after decoding (256 bits)

Generate a key with any of the following:

```bash
openssl rand -base64 32
```

or through the service API:

```csharp
string key = new EncryptionService(settings, logger).GenerateKey();
```

`AppSettingsValidation` rejects `EncryptionKey` values that are not valid Base64 or do not decode to 32 bytes. It also requires `EncryptionKey` when `EnableEncryption` is `true`.

## Behavior when encryption cannot run

This is the most important operational detail.

In `BackupService`, if `EnableEncryption` is `true` but the key is missing or invalid, the service logs a warning or error and skips encryption. The backup is then written and uploaded as plaintext with no `.enc` suffix and no failed run.

| Condition | Result |
|-----------|--------|
| `EnableEncryption` = `false` | Plaintext backup (expected). |
| `EnableEncryption` = `true`, key missing | Warning logged, plaintext backup uploaded. |
| `EnableEncryption` = `true`, key not a valid 32-byte Base64 value | Error logged, plaintext backup uploaded. |
| `EnableEncryption` = `true`, valid key | `.enc` backup uploaded. |

Monitor logs for `Skipping encryption` and check that uploaded file names end in `.enc`. A health check that only looks at whether backups run will not catch this.

## Restore and verification

`VerificationService` decrypts `.enc` backups into a temporary database during restore verification, using the same key resolution as the backup path. A backup encrypted with one key cannot be verified if the key has since changed. Keep every key that was used to produce backups you still need.

To restore manually, decrypt with `EncryptionUtility.DecryptFileAsync` or an equivalent OpenSSL command. The file is IV-prefixed, so the IV is the first 16 bytes:

```bash
KEY=$(echo -n "$BACKUP_ENCRYPTION_KEY" | base64 -d | xxd -p -c 64)
dd if=backup.sqlite.enc of=iv.bin bs=16 count=1 status=none
tail -c +17 backup.sqlite.enc > body.bin
openssl enc -d -aes-256-cbc -K "$KEY" -iv "$(xxd -p iv.bin | tr -d '\n')" -in body.bin -out restored.sqlite
```

If compression is also enabled, decompress the archive first.

## Security notes

- **No integrity protection.** CBC without an HMAC does not detect tampering. A modified ciphertext may decrypt to garbage or fail with a padding error, but it is not guaranteed to be rejected. Use storage-level integrity (S3 object checksums, Azure blob MD5) and the checksum recorded in `BackupManifest` as the integrity check.
- **Wrong key.** A wrong key usually fails with `CryptographicException` (padding error), but roughly 1 in 256 wrong keys will pass the padding check and produce garbage output. Always verify the restored database with `PRAGMA integrity_check`.
- **Key loss is unrecoverable.** There is no key escrow. Back up the key separately from the backups.
- **Key in memory.** `GetActiveKey()` and the resolved key are plain strings. Do not log them or include them in exception messages.
- **Key rotation.** Changing the key affects only new backups. Old `.enc` files still need the old key.
- **Storage-side encryption** (S3 SSE, Azure) is separate and can be used together with this feature.
